# WebHare 6.02 release notes

## Breaking changes

### OpenID Connect issuer is now derived from the identity provider site
WebHare no longer stores a configurable OpenID Connect `issuer` per WRD schema. The issuer is now always the webroot
of the site that has the `platform:identityprovider` webfeature for that schema, without the trailing slash (eg.
`https://login.example.net`). This is what RFC 8414 and OpenID Connect Discovery require: the issuer must match the
location the metadata is served from.

If your schema's previous issuer was different from that webroot (by default it was the backend URL), the `iss` claim
in ID tokens changes after the upgrade. Relying parties that have the old issuer configured will reject new
ID tokens until they are updated with the new issuer. Run `wh auth describe` to see the new value.

Whether a schema acts as an OpenID Connect provider is now controlled by `openIdServer` in the schema's
`loginSettings`. Schemas which had an issuer configured are migrated to `openIdServer: true` automatically.

You can enable or disable it with the 'OpenID Connect provider' checkbox on the OAuth tab of the WRD schema properties.

- `wh auth idp-setup` no longer accepts `--issuer`. It now only enables the schema as an OpenID Connect provider
- `initializeIssuer()` in `@webhare/auth` is deprecated and ignores its `issuer` parameter. Use `enableOpenIDServer()`
  instead
- `getOpenIDIssuer()` in `@webhare/auth` returns the issuer for a schema
- `getOpenIDMetadataURL()` now returns `null` if the schema isn't an OpenID Connect provider
- The keys returned by the JWKS endpoint no longer have an (unofficial) `issuer` property

### WRD API uses modern field names
The `/wrd/` endpoints of the WebHare API (`.wh/api/v1/`) now use the same field names as the modern `wrd()` API in
`@webhare/wrd`, instead of the legacy names. This applies to the fields you select in queries, the fields returned
in query results and the fields you pass when creating or updating entities:

| Legacy name           | New name            |
|-----------------------|---------------------|
| `wrdCreationDate`     | `wrdCreated`        |
| `wrdLimitDate`        | `wrdClosed`         |
| `wrdModificationDate` | `wrdModified`       |
| `wrdOrdering`         | `wrdOrder`          |
| `wrdInfix`            | `wrdLastNamePrefix` |

Requests that still use a legacy name now fail with an error. Update any integration that selects, reads or sends
these fields to use the new names.

The `wh wrd` commands have made the same switch: `export` and `get-setting` output the new names, and
`create-entity`, `update-entity` and `update-setting` expect them in their input.

### HareScript regular expressions now closely follow ECMAScript
`RegEx` from `wh::regex.whlib` now closely follows the syntax and behaviour of JavaScript's `RegExp`. Most patterns,
flags and replacement strings work the same in HareScript and in JavaScript/TypeScript (see the known differences
below). The native engine uses PCRE2 instead of the C++ standard library's `std::regex`. The WASM engine uses
JavaScript's `RegExp`, always in `u` mode (patterns without the `u` flag are translated).

Besides the `g`, `i` and `m` flags, the `u` (unicode) flag is now supported. Other flags, lookbehind assertions, named
capture groups and modifiers (eg `(?i:...)`) are not supported.

`JSRegEx` is deprecated. It is now identical to `RegEx`, so replace `NEW JSRegEx(...)` with `NEW RegEx(...)`.

Patterns that may behave differently:
- The `m` flag now works. Without it, `^` and `$` only match at the start and end of the input. Before, `m` had no
  effect.
- Patterns work on Unicode characters instead of bytes. For example, `.` matches `é` as one character. Positions
  (`start`, `len` and `lastindex`) are still UTF-8 byte offsets. Character classes containing non-ASCII characters used
  to match the individual bytes of those characters, so eg `[“”]` also matched parts of `—` and `‘`. They now only match
  the listed characters.
- POSIX character classes like `[[:alpha:]]` are no longer supported. As in JavaScript, `[[:alpha:]]` is now a class of
  the characters `[:alph` followed by a literal `]`. Replace them with explicit classes, eg `[a-zA-Z]`.
- With the `i` flag, non-ASCII letters now also match case-insensitively (eg `é` matches `É`).
- `\s` now also matches non-ASCII whitespace, like non-breaking spaces. `\d`, `\w` and `\b` still only match ASCII.
- A backreference to a group that didn't participate in the match now matches an empty string.
- `lastindex` follows JavaScript's rules. `Exec` and `Test` only use and update it for regular expressions with the `g`
  flag. A search from `lastindex` also looks at the text before it: `^` doesn't match there, but `\b` can. A
  `lastindex` inside a character continues at the next character.
- `Replace` and `ReplaceCallback` return the whole input, including any text before `lastindex`.
- Some patterns that used to throw are now accepted, as they are in JavaScript without the `u` flag:
  - a `{`, `}` or `]` that isn't part of a quantifier or class matches itself
  - unknown or incomplete escapes like `\A`, `\Q`, `\x4` or `\c1` mean the literal text
  - `\8` and `\9` mean the digits, and `\1` to `\7` without a matching group are octal escapes
  - a `-` next to a class escape (eg `[\w-a]`) is a literal `-`
  - a quantifier can follow a lookahead assertion (eg `(?=a)*`)

  Syntax that JavaScript rejects, like possessive quantifiers, atomic groups and `(?i)`-style inline flags, still
  throws.
- Error messages for invalid patterns have changed. They now start with `Invalid regular expression: /pattern/flags:`.

Known differences with JavaScript in both engines:
- Characters outside the Basic Multilingual Plane (eg emoji) are always a single character, also without the `u` flag.
  Without `u`, JavaScript sees them as two UTF-16 code units, so eg `.` only matches half of an emoji there.
- With the `i` flag, letters are always compared as JavaScript does with the `u` flag, so eg `ſ` (long s) matches `s`
  and `K` (Kelvin sign) matches `k`.

Known differences in the native engine:
- Without the `u` flag, a class range of characters outside the Basic Multilingual Plane (eg `[😀-🙏]`) isn't rejected.
  JavaScript (and so the WASM engine) rejects it, as it sees two UTF-16 code units. Use the `u` flag for such ranges.
- With the `u` flag, a quantifier on a lookahead assertion (eg `(?=a)*`) isn't rejected. Don't use it, as JavaScript
  doesn't allow it (so it doesn't work in WASM mode).
- U+2028 and U+2029 aren't line terminators.
- In `m` mode, `^` and `$` don't match between the CR and LF of a CRLF.
- With the `i` flag, `\w`, `\W`, `\b` and `\B` don't consider `ſ` (long s) and `K` (Kelvin sign) to be word characters.
  JavaScript does in `u` mode, and so does the WASM engine.

Building WebHare from source now requires PCRE2 10.43 or newer: `pcre2` from Homebrew, or `pcre2-devel` on Linux.

## OAuth2 and dynamic client registration
WRD schemas can now act as a plain OAuth2 authorization server without being an OpenID Connect provider. This is
enough for dynamic client registration (RFC 7591) and for MCP clients.

- `/.well-known/oauth-authorization-server` (RFC 8414) is served for every identity provider site
- `/.well-known/openid-configuration` is only served if `loginSettings.openIdServer` is enabled. Otherwise it
  returns 404, and the `openid`, `profile` and `email` scopes and the userinfo endpoint are unavailable.

## Validation
`wh validate` now also checks `.json` files (except `tsconfig.json`). Their JSON syntax is checked strictly (no
comments or trailing commas), and if their `$schema` property is a resource path (eg.
`mod::mymodule/data/settings.schema.json`) or a path relative to the file, they are validated against that schema.
YAML files without a module-specific validator are validated against their `$schema` in the same way.

`.schema.json`, `.schema.yml` and `.schema.yaml` files are compiled as a JSON Schema of the version in their `$schema`
property (draft-06, draft-07, 2019-09 or 2020-12, or 2020-12 if there's no `$schema`) in strict mode, so unknown
keywords are reported. Other `$schema` values, including draft-04, are reported as errors.

Files that passed validation before may now report errors. Exclude files that aren't meant to be valid JSON with an
`<exclude>` in your module's `<validation>` settings.
